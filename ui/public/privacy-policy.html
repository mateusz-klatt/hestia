Privacy Policy

Last updated: 21 November 2026

This policy covers Hestia at hestia.klatt.ie, operated by Mateusz Klatt. Hestia is a self-hosted smart-home and household application for the operator and invited users, not a public subscription service. The operator is the contact responsible for this installation and, where applicable data protection law requires it, its data controller. Contact: mateusz@klatt.ie.

Self-hosted means that application data are handled on the installation's server. It does not mean that data stay only in your browser or that enabled integrations never contact external providers. Independently operated copies of Hestia have their own operators and privacy arrangements.

Optional banking access is off unless the operator enables it. Hestia contains a read-only budget module that uses Enable Banking. It stays disabled until the operator explicitly configures and switches it on, and it covers only authorised accounts that are explicitly chosen for import or synchronisation. Section 4 describes what it handles.

1. Data handled by Hestia

  • Accounts and access: usernames, password hashes, roles, account status, authentication sessions and user preferences such as language, theme and temperature units. Login passwords are verified using salted scrypt hashes; Hestia does not need a readable copy of a user's application password after verification.
  • Devices and household activity: device and network identifiers, room names, device names, settings, commands and state reports. Depending on connected hardware, these can include temperature, humidity, motion or door states, heating settings and power readings. Automation rules can contain schedules, conditions and presence-related settings.
  • Activity and diagnostics: timestamps, user or automation actions, affected devices, results, connection information and error messages. Device protocols and diagnostic logs can contain device identifiers, state values and network addresses.
  • Optional calendars: events from explicitly selected Google or Apple/iCloud calendars, including authorised shared calendars. Data can include titles, notes, locations, dates, time zones, recurrence rules and exceptions, together with external identifiers, revisions, synchronisation status and deletion records. Event text may contain information about other people.
  • Integration configuration: selected accounts, calendar identifiers, service settings and credentials needed by enabled integrations. These can include Google OAuth credentials and refresh tokens, Apple app-specific credentials and local device keys. Secrets are configured on the server separately from the calendar event database.
  • Optional banking data: when the budget module is enabled, account balances, transactions and related status, control and audit records for authorised bank accounts chosen for import or synchronisation. Section 4 lists exactly what is kept.
  • Visits and contact: IP addresses and ordinary HTTP request metadata, including requested URLs, timestamps, headers and security signals, can be processed by the web server and reverse proxies. If you email the operator, your address and message are used to deal with your request.

Device and application state may be stored in server-side JSON files or SQLite, depending on configuration. Calendar events, mappings, pending operations and deletion records are stored in SQLite, and so is budget data when that module is enabled. Server logs, configuration files and operator-managed backups are separate forms of storage.

2. Purposes and control over optional features

Data are used to provide household device control, run requested automations, maintain accounts and permissions, remember preferences, synchronise selected calendars, troubleshoot faults and protect the installation. Calendar changes, including deletions, can propagate to the other calendars in a configured group.

External calendar synchronisation, outdoor weather requests and other optional integrations are enabled through configuration. Selecting a shared calendar can make its supported event content available to other connected calendars and authorised Hestia users. Application roles control actions; they do not provide a separate private calendar space for every household member.

Where the GDPR applies, necessary account, device, automation, diagnostic and security processing is based on the operator's legitimate interests in providing and securing the requested private household service, balanced against affected people's rights. Optional account connections require the account holder's authorisation and, where consent is the applicable data protection basis, their consent. Information about other people within authorised shared content is used only for the requested household purpose, on a lawful basis such as legitimate interests where applicable. Contact correspondence is handled to respond to requests and protect rights. This policy is not a blanket consent to additional uses.

Purely personal or household activities may fall outside the GDPR. That depends on the actual processing; it does not remove the separate responsibilities of external providers. Contact the operator about the purpose or basis applicable to particular data.

3. Who can receive data

  • Authorised household users and administrators: users can access household information within the application's available roles. The operator and people authorised to maintain the server or its backups may have administrative access.
  • Hosting, delivery and security: this deployment uses Cloudflare and an Apache HTTPS reverse proxy. These components handle requests and responses to deliver and protect the application, and can process request content, IP addresses and technical metadata. Cloudflare may apply security checks or necessary security cookies according to its configuration. See Cloudflare's privacy policy.
  • Calendar providers: when enabled, Google and Apple/iCloud receive authentication requests and the supported event data needed for synchronisation. Other people with access to a destination calendar may see the copied events under that calendar's sharing settings. See the Google privacy policy and Apple privacy policy.
  • Device vendor cloud in proxy mode: Hestia can relay device protocol traffic to the configured upstream vendor service. Standalone mode replaces that upstream device service; it does not turn off separately enabled external integrations.
  • Enable Banking and banks (only when budget access is enabled): Hestia sends authenticated read requests to Enable Banking for the selected accounts, and Enable Banking obtains the data from the bank. They receive the request details and network information needed for that access. See Enable Banking's privacy notice.
  • Optional network and weather services: enabling DNS-over-HTTPS resolution can send the queried hostname and server connection information to Google or Cloudflare resolvers. Enabling Open-Meteo weather sends configured latitude and longitude to Open-Meteo, which also receives the server's network address. See Open-Meteo's terms and privacy information.

Selling household data or using them for targeted advertising is not part of this service. External providers operate under their own terms and privacy notices. Their processing may take place outside your country, including outside the EEA; this installation does not promise exclusive EEA storage. Where data protection law applies, the operator must use appropriate transfer arrangements. Contact the operator for details relevant to an enabled integration.

4. Optional read-only banking access through Enable Banking

The budget module lets an account holder expressly authorise read-only access to their own bank accounts through Enable Banking, for private household budgeting such as reviewing spending and recurring charges. It is not a payment initiation, money transfer or financial advice service. It is off by default and runs only after the operator enables it.

Authorisation takes place through the bank and Enable Banking's authorisation flow. Do not enter bank passwords, PINs or one-time banking codes into Hestia. Hestia uses its own application key and the resulting authorised access session, not your online-banking login credentials. The application key and session identifiers are kept in files on the server that only the system account running Hestia can read. Externally provisioned credentials can be mounted read-only; browser-created sessions are written to a private persistent directory. The database keeps opaque file references rather than the credentials themselves. A browser authorisation return code is staged in a private file for a short-lived, single-use exchange. Failed or retired sessions may remain locally until the operator removes them; disconnecting does not erase history.

For authorised accounts that are explicitly chosen for import or synchronisation, Hestia stores the following in its SQLite database on this server. History imported from an earlier authorised download can be kept without enabling live synchronisation; importing and synchronising are separate choices.

  • Account references: a local identifier and the hashed account identifier issued by Enable Banking. Full account numbers and account-holder names from the bank's list of accounts are not stored as account details.
  • Optional account labels: the bank's product name, the account currency and the last four characters of the account identifier, so that the owner can recognise accounts. Product names that look like account numbers or identifiers are not stored.
  • Balances: amounts, currencies, balance types and when they were observed. Balances imported from earlier downloads are labelled separately.
  • Transactions: amount, currency, credit or debit, booking status, booking, value and transaction dates, the bank's reference and the free-text description lines supplied by the bank. Hestia keeps these lines as the bank sends them: they can contain names of shops or people, account numbers and other payment identifiers, and Hestia does not filter them. Entries that the bank reports ambiguously are kept apart as uncertain observations instead of being merged.
  • Origin and timing: whether data came from the bank interface or from an operator-imported copy of an earlier authorised download, and when they were observed, fetched and imported.
  • Controls and audit: which accounts are selected, confirmed account types, paused connections, the owner's choice of automatic refresh for each connection, the person and time of each change, and per-account request-limit and retry state used to respect the bank's access limits.
  • Refresh records: each requested or automatic refresh: who or what started it, when, which account and data type, its outcome and a technical key that prevents duplicate requests. Finished records become eligible for automatic cleanup after at least seven days; active work and backups may be kept longer.
  • Attention state: when the bank rejects authorisation, the access session is invalid or has expired, or the connection's configuration is wrong, Hestia marks the connection as needing attention and stops automatic refresh for it until a successful, explicitly requested check.

Hestia contacts the bank only for selected accounts, within the bank's access limits, when a refresh is requested or when the owner has enabled automatic refresh for a connection. Budget data are available through the Hestia interface only to the budget's owner, who must be signed in with an enabled administrator account; other users, including other administrators, cannot read them there. The operator has privileged access to the server, its database, files and backups. Budget pages and responses are delivered through the same Cloudflare and Apache reverse proxy as the rest of the application. The reverse proxy's access logs record requested addresses including their query part; for budget requests these contain Hestia's local identifiers, date filters and an encrypted paging token, not amounts, descriptions or bank identifiers. Hestia itself keeps no web access log and records budget errors only by error type. The SQLite database, its write-ahead log and backups are not encrypted by Hestia; they are protected by server file permissions and access controls.

Enable Banking provides the regulated account information service under its own terms and privacy notice. Its free restricted-production arrangement permits individual non-commercial access to the Control Panel user's own linked accounts, subject to its current terms; it is not permission to access other people's accounts or provide a public banking service. See Enable Banking's application terms, restricted account linking and end-user terms.

You can revoke bank access through the bank or Enable Banking's consent controls and ask the operator to disconnect it; the owner can also pause a connection or deselect an account in Hestia. Revocation, expiry, pausing or deselection stops future collection; it does not automatically erase copies already stored by Hestia. Deleting local data is a separate request, and providers manage their own records under their own obligations.

5. Retention, disconnection and deletion

Configuration and household records are retained while needed for the requested service, synchronisation integrity, troubleshooting or an applicable legal obligation. Retention depends on the type of record and operator settings. Activity logs have configurable age and row limits; pruning runs when new audit records are appended. Server logs and backups have their own operator-managed lifecycle. There is no single automatic deletion deadline for all Hestia data.

Calendar deletion is not complete local erasure. A deleted event is marked inactive, and its existing event payload, external mapping and durable deletion record can remain in SQLite. Deletion records are kept permanently in normal operation to stop an old external copy from recreating the event. Pending operations may also survive restarts.

Banking history has no automatic deletion deadline. Transactions, balances, account labels and their audit records stay in SQLite and in backups until the operator removes them on request. Only finished refresh records are cleaned up automatically, as described in section 4.

Disconnecting an integration or revoking a provider token does not erase previously stored records, provider-side copies or backups. For full removal, contact the operator so that local records, synchronisation mappings, external copies and backups can be considered together. Deletion requests are assessed against applicable rights and obligations; the software's default retention is not a refusal of a lawful erasure request.

6. Browser storage and security

When sign-in is enabled, Hestia issues the necessary hestia_session cookie, currently with a 30-day expiry. It is signed, HttpOnly and SameSite=Strict. Its Secure flag depends on deployment configuration. Native clients can use an equivalent bearer token. Browser local storage remembers the selected dashboard view; user preferences can also be stored on the server. Logging out clears the browser's Hestia cookie; it does not erase household records. Connecting a bank additionally creates a necessary per-flow cookie named __Host-hestia_budget_… for up to 15 minutes. It is Secure, HttpOnly and SameSite=Lax, so the bank's return can be tied to the same browser while the main session stays Strict. Login and logout invalidate matching unfinished flows.

These legal pages contain no JavaScript, external fonts, advertising or analytics resources. This does not prevent ordinary hosting/security processing or an existing session cookie from being sent with a page request.

Protection relies on account permissions, server and network controls, secret handling and backup practices. Hestia does not provide a general encryption-at-rest layer for its SQLite databases, configuration files or backups. Some supported legacy device protocols are unencrypted. HTTPS delivery does not make those device links, server storage or provider processing end-to-end encrypted.
